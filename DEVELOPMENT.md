# Developer guide

Technical reference for the UNMC Research Administration Data Governance
repository: the governance data, and how it becomes the published site. If
you're here to *read* or *suggest a change to* a term, you want the
[published site](https://unmc-vcr.github.io/data-governance/), not this file;
see the [README](README.md).

## The core idea: governance is data

The terms, the offices and council that govern them, and each term's lifecycle
are YAML data written against the
[Data Governance Ontology](https://github.com/james-geiger/dgo) (DGO). This
repository holds no schema and no site generator of its own:
[dgo-atlas](https://github.com/james-geiger/dgo-atlas) validates the data and
builds the site. Rewording a definition is a data change; changing what a term
*can* say is a change to DGO.

## Quick start

```bash
uv sync
uv run dgo-atlas build
```

The site lands in `site/`. Open `site/index.html` directly — it uses relative
links throughout and needs no web server. To preview with a server instead:

```bash
python3 -m http.server 8137 --directory site
```

Other commands:

| Command | What it does |
| --- | --- |
| `uv run dgo-atlas validate` | Checks the data without building. |
| `uv run dgo-atlas text` | Lists every piece of site wording and its key, for `text:` in `dgo-atlas.yaml`. |

## Repository layout

| Path | What it is |
| --- | --- |
| `dgo-atlas.yaml` | Site configuration: the DGO release, title, identifier prefixes, branding, wording overrides. |
| `governance/organization.yaml` | The governance process, the council, people, offices, and council roles. |
| `governance/glossary.yaml` | The business glossary and the definition sources. |
| `governance/research_administration/research_administration.yaml` | The Research Administration domain. |
| `governance/research_administration/<area>/<area>.yaml` | A subject area. |
| `governance/research_administration/<area>/terms/*.yaml` | The governed terms, **one file per term**, each with its lifecycle. |
| `content/**.md` | Authored narrative: the hub, the governance guide, standards. |
| `.dgo-atlas/*.schema.json` | Editor validation schemas, generated by dgo-atlas. Don't edit; commit them. |

Every `.yaml` file under `governance/` is merged, so a subject area is just a
new directory. Only governance data may live there.

## Versions

`pyproject.toml` pins dgo-atlas to a release tag, and `dgo_version` in
`dgo-atlas.yaml` names the DGO release the data is written against. Change
either deliberately: a new DGO release may change what the data must say.

## Adding or changing a term

1. Edit the term's file under `governance/research_administration/<area>/terms/`,
   or add a new one. Copy an existing term file as a template.
2. Run `uv run dgo-atlas build` locally. Fix whatever it complains about.
3. Open a pull request. CI validates, builds, and uploads a preview of the site.
4. The steward office reviews the **rendered pages**, not the YAML diff.
5. Merge.

`.github/CODEOWNERS` routes each subject area's directory to its steward
office, so the right reviewers are requested automatically.

### Authoring rules

The build enforces these:

- **Ids are CURIEs** using a prefix from `dgo-atlas.yaml` (`term:`, `area:`,
  `office:`, `person:`), except definition sources, whose id is the source's own
  IRI. Ids are the terms' IRIs: never change one.
- **Every term** has a `label`, a `definition`, `part_of: area:research-glossary`
  and one `in_subject_area`.
- **`type` values are DGO class IRIs**, with the readable name in a comment
  (`dgo:DGO_00000012   # owner`). `dgo:Owner` is rejected.
- **Quote every date:** `occurred_on: "2026-09-28"`.

### Term state

There is no status field. A term's state follows from its **term creation**
(in the same file as the term) and the dated **status boundaries** on it. A term
with no term creation is not published at all.

| Boundaries on the creation | Shown as |
| --- | --- |
| drafted (`dgo:DGO_00000024`) | Proposed |
| drafted, submitted for review (`dgo:DGO_00000025`) | Proposed |
| …, approved (`dgo:DGO_00000026`) | Approved |
| a `term_deprecations` entry with an approved boundary | Deprecated |

To move a term forward, add a boundary with the date it happened. To change an
approved term, edit it in place and record a `term_modifications` entry. Never
delete a term: deprecate it and set `replaced_by`.

`definition_source` is optional. It records where wording was *adopted from*,
so a definition authored at UNMC correctly has none.

### Governance roles

Responsibility attaches to an **office** or the council, never a named
individual — an office IRI survives staff turnover. Each term's
`responsibilities` list names who holds each role:

| Role | `type` |
| --- | --- |
| owner | `dgo:DGO_00000012` |
| steward | `dgo:DGO_00000013` |
| custodian | `dgo:DGO_00000014` |
| subject matter expert | `dgo:DGO_00000015` |

## Editor validation

Install the [Red Hat YAML extension](https://marketplace.visualstudio.com/items?itemName=redhat.vscode-yaml)
(`redhat.vscode-yaml`) — VS Code offers it from `.vscode/extensions.json`.
`.vscode/settings.json` maps `governance/**/*.yaml` and `dgo-atlas.yaml` to the
schemas in `.dgo-atlas/`, so an unknown key or a missing required field is
underlined as you type. dgo-atlas rewrites those schemas on every build; commit
them when they change. They check shape only: references are resolved by the
build.

## CI/CD

`.github/workflows/site.yml` publishes to **GitHub Pages**.

- **Every pull request** — `uv sync`, then `uv run dgo-atlas build` (which
  validates, builds, and checks every internal link), and upload the site as the
  `site` artifact. Download it, unzip, open `index.html`. Nothing deploys.
- **Push to `main`** — the same, then deploy to Pages.

`base_path: /data-governance/` in `dgo-atlas.yaml` matches the Pages project
site. Only `404.html` depends on it; a custom domain would use `/`.

## Known gaps

- **The council's `email`** has no slot in DGO v0.1.1, so it is written as a
  comment until DGO adds one.
- **dgo-site 0.1.0 predates DGO v0.1.1.** It validates a term's
  `semantic_types` and an office's `has_member`, but does not show them on the
  site yet, and it warns that it has not been tested with v0.1.1.
- **Lifecycle dates are placeholders.** Every status boundary was dated on the
  day of the migration to dgo-site (2026-09-28), not the day it happened.
- **The namespace is not registered yet.** `https://w3id.org/unmc/` is not
  registered, so IRIs do not resolve.
- **Data classification is provisional.** The four tiers and the handling
  matrix in `content/standards/data-classification.md` have **not** been
  approved by Compliance & Privacy.
- **`CODEOWNERS` uses placeholder team handles.** GitHub does not warn about an
  unknown owner — the rule is silently ineffective. Create the teams and verify
  with a test PR.
- **The published site is anonymous.** Pages serves it to anyone with the
  link, so everything in `governance/` is public once the repository is.
- **`term:clinical-study` has a TODO definition.** It cannot be approved until
  it is written.
